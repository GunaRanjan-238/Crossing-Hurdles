# Allow disabling upload checksums while still using the upload review callback

The aws-c-s3 client lets callers register an `upload_review_callback` that is invoked before a multipart upload is completed so they can confirm that the parts being sent match the per-part checksums they expect (detecting corruption that happened while parts sat in CRT memory). Today, however, the client couples "compute checksums" with "send checksums": if a caller sets a checksum algorithm but a checksum location of `AWS_SCL_NONE`, the request is rejected outright, and there is no way to compute checksums purely for review without also transmitting them to S3. Some clients (for example Mountpoint) talk to S3-compatible endpoints that do not support the additional-checksums feature, yet still want the review callback to run over per-part checksums. Your job is to make that possible: when the checksum location is `AWS_SCL_NONE` but an upload review callback is registered, the client should still compute per-part checksums, invoke the review callback normally (including the per-part checksums), and simply omit the checksums from the requests it sends to S3.

The change spans `source/s3_client.c`, `source/s3_checksum_stream.c`, `source/s3_request_messages.c`, `source/s3_auto_ranged_put.c`, `source/s3_copy_object.c`, and `include/aws/s3/private/s3_request_messages.h`. The following acceptance criteria describe the observable behavior expected of the finished change:

1. Given a meta request configured with a checksum algorithm other than `AWS_SCA_NONE` and a checksum location of `AWS_SCL_NONE`, when an upload review callback is registered on the request, then `aws_s3_client_make_meta_request` should accept the configuration and proceed rather than failing. When that same algorithm-set / location-`AWS_SCL_NONE` combination is supplied with no upload review callback, the request must still be rejected with `AWS_ERROR_INVALID_ARGUMENT`, and the emitted error log should explain that a checksum algorithm was set but no location was selected and no upload review callback was set, so the checksums would go unused.

2. Given the location-`AWS_SCL_NONE`-plus-review-callback configuration, when a part body stream is assigned in `aws_s3_message_util_assign_body` and an out-checksum buffer is provided, then the client should still wrap the body in a checksum stream so a per-part checksum is computed for the review callback — even though the computed checksum will not be attached to the outbound request. The out-checksum buffer must be sized from the algorithm's digest size via the base64-encoded length, and any allocation or setup failure must clean up and fail the same way other errors in that function do.

3. The `aws_checksum_stream` should finalize its checksum at the end of the stream rather than only on destruction. When a read consumes the last bytes of the underlying stream (its status reports end-of-stream), the stream should compute the final checksum and base64-encode it into the caller's output buffer exactly once; a second finalize attempt must be a no-op. Finalization must be idempotent regardless of whether it is triggered by reaching end-of-stream during a read or by the stream being destroyed before end-of-stream was reached.

4. If finalizing the checksum fails, the stream must not abort the process. Instead it should reset the checksum result buffer, log an error that includes the underlying error code and its string form, mark the checksum as finalized, and raise `AWS_ERROR_S3_CHECKSUM_CALCULATION_FAILED`. A read that successfully updates the running checksum but is not yet at end-of-stream should return success.

5. The internal message constructors operate on the full checksum configuration rather than a bare algorithm enum. `aws_s3_create_multipart_upload_message_new` and `aws_s3_complete_multipart_message_new` accept a `const struct checksum_config *` parameter. A `NULL` config (or one whose location is `AWS_SCL_NONE`) results in no checksum headers being added. The create-multipart request sets the checksum algorithm header only when a config is present with a non-`AWS_SCA_NONE` algorithm and a location other than `AWS_SCL_NONE`. The complete-multipart request selects the algorithm's completion checksum name and uses the with-checksum excluded-headers set only when the config's location is not `AWS_SCL_NONE`; otherwise it uses the plain excluded-headers set.

All callers must pass the checksum configuration that reflects what they intend to send. The paths that can legitimately carry client-computed checksums (creating the multipart upload for both the auto-ranged-put and copy-object flows, and completing the auto-ranged-put) pass their meta request's own checksum configuration. The copy-object completion path never uploads client-computed checksums, so it passes no configuration at all.

A resulting object uploaded under location `AWS_SCL_NONE` with a review callback should carry no checksum for S3 to validate on a later GET, while the review callback should have been invoked once with the correct per-part count, sizes, algorithm, and per-part checksum values.
